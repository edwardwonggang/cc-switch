# Codex 多供应商模型路由

此改造在 Codex 接管模式下按精确模型名选择供应商，让配置好的多个供应商同时服务不同模型。开关默认为关闭；关闭或模型未在目录中声明时保留原当前供应商及故障转移策略。

## 行为与边界

- 候选来自供应商各自的 `settingsConfig.modelCatalog.models[].model`，区分大小写；无目录时仅使用明确配置的上游默认模型。
- 重复模型遵循现有供应商稳定顺序。启用故障转移时，只在支持该模型的候选中重试；不把别的模型供应商当成兜底。
- 按模型选择或恢复供应商不会重写全局当前项，不改变托盘选择，避免并发请求串改默认供应商。
- 目录逐供应商生成再合并，保留各自工具协议、上下文和推理参数；重复模型只保留首选供应商的完整条目。
- 官方账号透传卡保持原有账号边界，不复用其 OAuth 身份作为普通模型路由候选。
- UI 位于 Codex 代理设置，只有接管启用时才能打开。设置键为 `codex_model_routing_enabled`，没有迁移或清空供应商表。
- Claude、Gemini 和其他客户端的既有策略不变。

## 验证

隔离数据库和本地 HTTP 假上游验证了 Responses/Chat 两种供应商并发、独立凭证、同模型候选故障转移、未知模型默认、关闭回退及当前供应商不变。目录测试验证了协议相关字段保留和同名优先级，前端开关测试覆盖读取、成功和失败回执。

本轮已有的验证结果：模型路由定向测试4项通过；TypeScript检查通过；前端138文件、1109项测试通过。后端完整 lib 运行中2875项通过、5项忽略、1项既有 Claude Desktop 测试因本机15721端口占用失败，该结果不能描述为全量通过。随后直接复用既有测试产物重跑4项隔离模型路由检查，真实用户数据库和设置的哈希、大小、mtime前后不变。

Windows安装包由 GitHub Actions 的 `Release (Windows x64, unsigned)` 工作流构建。本次不在用户 Windows 本地编译或替换安装中的可执行文件；以 Actions 运行和最终产物为准。真实供应商连通、运行配置启用和部署后行为仍需使用对应产物验证。
